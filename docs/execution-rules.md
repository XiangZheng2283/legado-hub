# LegadoHub 执行协作规则

## 角色分工

- Codex：只负责规划、方案审核、代码审查、验收标准定义和验收结果判断。
- Kimi：负责具体实现、文件修改、运行验证、问题修复和阶段交付。

Codex 不直接实现业务代码，除非用户明确改变分工。

## 执行方式

- 每个阶段由 Codex 在当前会话回复中产出一个 `/goal` 命令块，不再为 goal 单独创建文档。
- `/goal` 写法按 Codex 常规 goal 指令：使用 `text` 代码块包裹，第一词为 `/goal`，尽量保持一行，明确工作目录、阶段目标、角色边界、规划文档路径、自测和交付要求。
- 用户将代码块中的 `/goal` 直接交给 Kimi 执行。
- Kimi 完成后返回：
  - 修改文件清单
  - 运行命令
  - 验证结果
  - 未完成项或阻塞
- Codex 根据计划和验收标准做审查。

## 项目边界

- 项目根目录：`C:/Home/Workspace/UGit/legado-hub`
- 第一阶段只做 Windows 本地脚本运行。
- Docker 后置。
- 第一阶段不做完整 Web 管理台。
- 阶段 2 开始做后端 Web 调试/浏览界面。

## 实现约束

- 默认使用 Python。
- 第一阶段优先 FastAPI + SQLite。
- 不引入复杂前端构建链，除非阶段 2 明确需要。
- 不直接搬运 Android/Kotlin 阅读引擎。
- 阅读原生仓库只作为规则语义参考。
- `freeok/so-novel` 只作为规则模型和站点适配参考，不作为唯一引擎。
- 生成给阅读端导入的是单条聚合书源 JSON。

## 质量门禁

每个阶段完成前必须提供：

1. 可复现启动命令。
2. 实际运行过的验证命令。
3. 关键接口验证结果。
4. 失败项说明。
5. 文件变更范围。

没有验证证据，不得声明完成。

## Git 规则

- 当前项目未初始化 Git 时，不强制提交。
- 不执行 `git init`、`git commit`、`git push`，除非用户明确要求。
- 不删除用户提供的参考文件。

## 文档同步

实现导致阶段目标、接口、目录结构或依赖变化时，Kimi 必须同步更新对应文档：

- `docs/project-plan.md`
- `docs/implementation-plan-phase-1.md`
- 后续阶段的实施计划文档
