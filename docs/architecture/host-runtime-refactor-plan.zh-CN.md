# 宿主层重构与存储收口方案

> 状态：讨论收口版  
> 范围：`legado-hub` 宿主层  
> 不包含：`QDFCCKK` 插件源码改动

---

## 1. 背景

当前项目已经具备可运行的宿主层、插件层、搜索任务、聚合任务、登录态管理和缓存能力，但也逐步暴露出几个结构性问题：

1. 搜索请求会裂变成大量下游请求，宿主层缺少统一调度与总量控制。
2. SQLite 中混入了大量实时态、调试态、过程态数据，数据库职责不清。
3. 配置、Cookie、运行状态分散在数据库、插件目录和多个文件中，真相源不统一。
4. 代理策略过宽，容易把本应直连的书源也拉入代理链路。
5. 当前实现更偏“功能堆叠”，不利于继续往 50 人并发搜索场景推进。

本方案用于统一前几轮讨论结果，明确宿主层接下来的架构方向。

---

## 2. 总体原则

### 2.1 先改架构，不先迁语言

当前阶段不优先迁移到 Go 或 Rust。  
先在 Python 宿主层内完成调度、缓存、存储、代理和登录态边界的重构，再根据压测结果决定是否迁语言。

### 2.2 配置进文件，事实进数据库，过程进日志或内存

宿主层后续统一采用以下分层：

1. **配置文件**：稳定、小体量、人工可编辑的配置。
2. **数据库**：长期复用的业务事实数据。
3. **内存 / 日志**：实时运行状态、调试数据、过程事件。

### 2.3 本轮直接收口，不做兼容

这次宿主层重构按“直接收口”执行，不做旧路径兼容、不做数据库字段兼容、不做回退层。

具体原则：

1. 数据库不需要的表和字段直接删除。
2. 不再为旧 `search_job_events`、旧插件健康状态、旧登录状态缓存保留兼容读取。
3. 不再保留插件目录 `Cookie.json` 作为有效路径。
4. 不再通过 `ALTER TABLE` 继续补丁式叠字段来兼容旧模型。
5. 若数据库结构已不适合新架构，则直接重建，不做平滑迁移。

### 2.4 宿主管运行，插件管解析

宿主负责：

- 搜索调度
- 并发控制
- 缓存策略
- 配置管理
- Cookie 文件管理
- 结果存储
- 日志与调试入口

插件负责：

- 请求某个 URL
- 解析返回内容
- 定义自己的 Cookie payload 结构
- 基于 Cookie payload 做实时登录态探测

## 3. 搜索架构方案

### 3.1 搜索模型

搜索不再采用“每个任务创建后立刻全源开跑”的方式，而改成宿主统一调度。

新增宿主层 `SearchCoordinator`，统一负责：

- 接收搜索任务
- 任务去重
- 公平并发
- 源级限流
- 分阶段返回结果
- 低频持久化

### 3.2 目标并发模型

目标不是“所有任务同时全量并发”，而是“所有请求都能进入系统，然后按额度公平推进”。

建议模型：

1. 请求进入后立即返回 `jobId`。
2. 所有任务进入统一队列。
3. 同一时刻仅允许有限数量的真实搜索任务运行。
4. 每个任务先分配少量快源额度。
5. 快源先回，慢源后补，浏览器源单独限流。

### 3.3 并发控制

宿主层需要至少三层额度控制：

1. **任务级额度**
   - 同时真正运行的搜索任务数受限。
2. **全局源级额度**
   - 同时打出去的外部请求总数受限。
3. **站点级额度**
   - 同一站点并发数受限。
4. **浏览器源额度**
   - 浏览器 / 风控绕过类书源单独限流。

### 3.4 搜索分阶段

每个搜索任务按以下顺序执行：

1. 第一阶段：快源、稳定源优先，尽快返回首批结果。
2. 第二阶段：普通源补全。
3. 第三阶段：慢源、浏览器源、容易超时的源按需补充。

目标是优先改善用户体感，而不是一开始就追求全量完成。

### 3.5 同词任务合并

对相同：

- `normalized keyword`
- `page`
- `source scope`

的搜索任务，直接复用现有任务和结果，不重复全站 fan-out。

### 3.6 正常搜索与调试搜索

#### 正常搜索

1. 先查缓存 / 搜索结果库。
2. 命中后优先返回缓存结果。
3. 后台继续实时搜索。
4. 若站点信息有变化，则更新数据库。

#### 调试搜索

后台搜索页增加 `bypassCache` 开关：

- 仅跳过“读缓存”
- 不跳过写回数据库
- 仅后台入口可用
- 用于测试真实书源行为

### 3.7 搜索结果记录方式

搜索不再重点保存过程事件，而是重点保存：

- 该书在该站点是否命中
- 对应书籍地址
- 归一化后的核心字段
- 原始 payload 或标准化 payload

搜索的本质是建立“自身搜索数据库”，而不是记录过程流水账。

## 4. 存储分层方案

### 4.1 文件配置

所有常规配置统一放到：

```text
backend/config/
```

并尽量合并为少量主配置文件，不再一个功能一个文件到处散。

建议：

```text
backend/config/
├── app_config.json
└── cookies/
    ├── qidian_com_web.json
    └── qidian_com_app.json
```

#### `app_config.json`

统一包含：

- 代理配置
- 搜索调度配置
- 聚合配置
- AI 配置
- 后台设置项
- 调试开关
- 过滤阈值
- 快源/慢源策略

要求：

1. 常规配置尽量合并到一个主文件中，不再一个设置项一个文件。
2. 已迁到本地文件的配置后续并入主配置文件，避免多真相源。
3. 宿主运行策略统一只从该主配置读取。

### 4.2 Cookie 文件

Cookie 文件由宿主统一管理，不再让插件自己在插件目录下读写 `Cookie.json`。

规则：

1. 路径统一放在 `backend/config/cookies/`
2. 文件按 `plugin_id` 命名
3. 文件内容结构由插件决定
4. 宿主只提供统一读写接口，不理解内部字段

例如：

```text
backend/config/cookies/qidian_com_web.json
backend/config/cookies/qidian_com_app.json
```

宿主提供统一接口：

- `load_cookie_payload(plugin_id)`
- `save_cookie_payload(plugin_id, payload)`
- `clear_cookie_payload(plugin_id)`
- `has_cookie_payload(plugin_id)`

插件负责：

- 定义该 JSON 的内部结构
- 将 payload 转为运行时 cookie jar
- 基于 payload 执行实时 `auth_status`

### 4.3 数据库

数据库只保留长期复用的事实数据。

推荐保留的数据：

1. 搜索结果映射
2. 书籍基础信息索引
3. 站点书籍地址映射
4. `book_cache / toc_cache / chapter_cache`
5. 聚合任务与聚合结果
6. 必要的书架 / 更新任务

### 4.4 日志与实时状态

下列数据不再作为主数据库数据：

- 搜索事件流
- 插件健康状态
- 插件尝试过程
- 实时代理状态
- 搜索过程历史
- 登录探测过程

这些数据应该进入：

- 内存 ring buffer
- 调试日志
- 可清理的 JSONL / 文本日志

例如：

```text
backend/runtime/logs/search/
backend/runtime/logs/auth/
backend/runtime/logs/debug/
```

## 5. 数据库瘦身方向

### 5.1 需要保留的主数据

以下内容属于长期有复用价值的事实数据，建议保留：

1. 书籍基础信息与地址映射
2. 搜索结果快照或结果索引
3. 内容缓存
4. 聚合结果
5. 必要的更新任务与书架数据

### 5.2 明显不应继续作为主库数据的内容

以下数据原则上应出主库：

1. `plugin_health`
2. `plugin_attempts`
3. `search_job_events`
4. `plugin_runtime_state`
5. `plugin_auth_state`
6. 逐次搜索历史
7. 逐次插件过程日志

这些内容若仍有调试价值，统一转入：

- 内存 ring buffer
- `backend/runtime/logs/`
- 可清理的 JSONL / 文本日志

### 5.3 搜索子系统数据库重构方向

搜索相关表建议重建为更简单的结构：

1. `search_jobs`
   - 只保留任务摘要
2. `search_results`
   - 记录每本书在每个站点的命中信息
3. `search_query_cache`
   - 保存关键词级结果快照

默认不再保留 `search_job_events`。

### 5.4 登录态存储方向

登录态不应作为数据库中的长期真相源。

建议：

1. `Cookie` 文件是唯一凭据来源
2. 当前是否已登录，完全依赖实时 `auth_status`
3. 启动时如发现 Cookie 文件，可做一次探测
4. 不再把 `authenticated / pending / anonymous` 作为长期数据库状态保存

也就是说，`plugin_auth_state` 后续应废弃或极度收缩。

### 5.5 数据库处理方式

本轮建议直接重建宿主数据库，而不是做兼容迁移。

建议做法：

1. 停止宿主服务。
2. 删除旧 `app.db`。
3. 用新 schema 直接初始化。
4. 清理旧搜索表、旧健康状态表、旧登录状态表对应代码。
5. 不保留旧表只读桥接。

## 6. 代理策略调整

### 6.1 当前问题

当前代理逻辑过宽：只要全局代理开着，很多 `proxy.mode = auto` 的书源都会被纳入代理可用链路。

这会导致：

1. 资源占用抬高
2. 调试复杂度增加
3. 直连源也被不必要地拉入代理重试

### 6.2 调整方向

代理语义改成：

1. **默认直连**
2. 只有明确配置需要代理的书源才允许代理
3. 宿主统一控制代理额度
4. 浏览器源、代理源、直连源分车道调度

具体规则：

- `never`：始终直连
- `always`：始终代理
- `auto`：仅用于少数明确需要“失败后代理重试”的书源

全局存在代理配置，不再等于“所有书源默认都可代理”。

### 6.3 配置方式

代理策略应收进统一配置文件，不再由数据库保存为运行中状态真相源。

## 7. 插件与宿主边界

本轮宿主层重构后，插件定义和宿主边界需要同步重写，不能继续沿用旧文档里的部分假设。

需要跟随本轮一起整理的文档：

1. `docs/architecture/source-plugin-contract.zh-CN.md`
2. `docs/architecture/source-plugin-contract.md`
3. `plugins/templates/source_plugin/README.md`
4. `docs/architecture/repository-layout.md`

需要同步修正的插件规范：

1. 插件不再管理自己的 Cookie 文件路径。
2. 插件只能通过宿主提供的 Cookie 接口读写 payload。
3. Cookie 文件按 `plugin_id` 命名，内容结构由插件定义。
4. 登录状态由插件实时探测，不再依赖数据库状态。
5. 插件不再假设搜索过程事件会落库。
6. 插件不再假设宿主会持久化插件健康状态。
7. `proxy.mode` 的默认语义需要收紧为更保守的直连优先模型。

### 7.1 宿主负责

- 搜索调度
- 限流与并发
- 配置管理
- Cookie 文件管理
- 数据库存储
- 日志与调试接口
- 代理策略执行

### 7.2 插件负责

- `search`
- `detail`
- `toc`
- `chapter`
- `reviews`
- `auth_status`
- 自己的 Cookie payload 结构
- payload 到运行时 cookie jar 的转换

插件不负责：

- 数据库
- 调度
- 全局缓存
- 任务管理
- 全局代理策略

## 8. 语言与迁移判断

### 8.1 当前阶段

当前阶段不优先迁 `Go` 或 `Rust`。

原因：

1. 当前主要瓶颈是架构，不是语言。
2. 即使迁移语言，如果搜索模型不改，收益会被吞掉。
3. 对当前项目规模，Python 仍然可以先把调度、限流、缓存、存储这一层做好。

### 8.2 何时再评估 Go

以下情况再认真评估迁 Go：

1. 需要承载远高于当前目标的并发
2. 需要多机 worker 和分布式任务系统
3. Python 宿主层在架构重构后仍明显吃力

## 9. Access Bridge 转接性能评估

### 9.1 结论

“请求走一遍 `access_bridge` 转接会不会有明显性能损耗”要分路径看：

1. **普通 HTTP 路径**
   - 损耗很小。
   - `ctx.access.http` 最终还是直接调用宿主 `Fetcher`。
2. **stealth HTTP 路径**
   - 相比普通 HTTP 只多一层 header / impersonate 处理，损耗仍然较小。
3. **browser 路径**
   - 损耗很大。
   - 真正重的是 Playwright / Browserless 的连接、上下文创建、页面加载，而不是 facade 本身。

### 9.2 当前实现观察

当前访问层结构是：

1. `ctx.access.http`
   - 直接调用 `Fetcher.fetch_*`
2. `ctx.access.stealth`
   - 本质上仍委托给 `ctx.access.http`
3. `ctx.access.browser`
   - 才真正走 `AccessBridgeClient.fetch()`

因此：

1. 普通 `GET` 请求不会天然走浏览器桥。
2. Access Bridge facade 本身不是主瓶颈。
3. 需要警惕的是 facade 附带的副作用：
   - `ctx.cookies._persist()`
   - trace 记录
   - 若后续仍保留高频文件/数据库写入，会放大这层成本

### 9.3 宿主层建议

1. 普通 HTTP 不需要绕开 `ctx.access.http`
2. 需要优化的是：
   - Cookie 持久化频率
   - trace 写入频率
   - 浏览器路径误用
3. 后续压测应单独区分：
   - 直连 HTTP
   - stealth HTTP
   - browser bridge

### 9.4 最终判断

对当前项目来说：

1. `access_bridge` 普通 HTTP 转接的性能损耗相对网络请求本身可忽略。
2. 真正重的是浏览器桥和高频副作用。
3. 后续优化重点不是删掉 facade，而是避免普通请求误入浏览器链路，并减少 facade 后面的持久化动作。

## 10. 执行步骤与执行细节

### 阶段 1：配置与 Cookie 收口

目标：

1. 把宿主常规配置统一收口到 `backend/config/app_config.json`
2. 把 Cookie 文件统一收口到 `backend/config/cookies/<plugin_id>.json`
3. 删除插件目录 Cookie 管理路径

执行细节：

1. 设计新的主配置 JSON 结构。
2. 合并现有零散配置来源。
3. 新建宿主级 CookieStore。
4. 替换调度器、登录管理、插件上下文中的旧 Cookie 读写逻辑。
5. 删除插件目录 `Cookie.json` 相关路径判断。

### 阶段 2：数据库直接重建

目标：

1. 删除不再需要的实时态、调试态、过程态表
2. 重建搜索相关表
3. 停止继续维护旧 schema 兼容层

执行细节：

1. 重写 `db.py` 中的搜索和运行态相关 schema。
2. 删除：
   - `plugin_health`
   - `plugin_attempts`
   - `search_job_events`
   - `plugin_runtime_state`
   - `plugin_auth_state`
3. 重建搜索结果导向表：
   - `search_jobs`
   - `search_results`
   - `search_query_cache`
4. 删除旧数据库后直接初始化新库。

### 阶段 3：搜索调度器重写

目标：

1. 引入 `SearchCoordinator`
2. 实现任务级并发上限、源级限流、同词任务合并
3. 改成缓存优先、后台刷新、结果导向存储

执行细节：

1. 搜索入口不再直接 `create_task(run_job)`。
2. 统一由协调器接管任务生命周期。
3. 同一关键词任务优先复用。
4. 每个任务按快源 -> 普通源 -> 慢源分阶段执行。
5. 过程事件默认不落库。

### 阶段 4：代理策略收紧

目标：

1. 默认直连
2. 仅显式代理
3. 浏览器源、代理源、直连源分车道

执行细节：

1. 重写宿主代理决策逻辑。
2. 删除数据库代理运行态真相源。
3. 将代理策略收进主配置文件。
4. 清理旧 `auto` 语义。

### 阶段 5：插件规范与模板重写

目标：

1. 让插件契约和新宿主边界一致
2. 删除旧 Cookie / 事件流 / 健康状态相关假设

执行细节：

1. 改写插件协议文档。
2. 更新插件模板。
3. 明确 `ctx.access.http / stealth / browser` 的使用边界。
4. 明确插件只能通过宿主 Cookie 接口读写 payload。

### 阶段 6：压测与验证

目标：

1. 验证 10 / 20 / 50 并发搜索
2. 验证普通请求不会误入浏览器桥
3. 验证配置、Cookie、数据库边界已经收口

重点验证项：

1. 首批结果返回时间
2. 完整完成时间
3. 数据库写入次数
4. CPU / 内存波动
5. 直连 HTTP / stealth / browser 三条路径的耗时差异

## 11. 实施顺序

建议按以下顺序推进：

1. 统一配置到 `backend/config/app_config.json`
2. 统一 Cookie 到 `backend/config/cookies/<plugin_id>.json`
3. 直接重建数据库 schema
4. 新增 `SearchCoordinator`
5. 加入任务级并发上限与源级限流
6. 实现快源优先、慢源后补
7. 实现同词任务合并
8. 将搜索结果模型改为“结果导向持久化”
9. 清理搜索事件流数据库写入
10. 收紧代理策略为“默认直连，仅显式代理”
11. 重写插件协议与模板
12. 最后再视情况考虑语言迁移

---

## 12. 最终收口

本轮讨论的最终共识可以压缩成下面三句话：

1. **先改宿主层架构，不先迁语言。**
2. **配置进文件，事实进数据库，过程进日志或内存。**
3. **Cookie、搜索、代理、登录态都由宿主统一收口，插件只管解析和实时探测。**
